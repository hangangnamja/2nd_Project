## 2-1. 속도와 턴 (행동 순서)

**모두 같은 거리를 달리고, 먼저 도착한 유닛이 행동한다** (붕괴 스타레일식)

- 유닛마다 **남은 거리**를 가짐. 전투 시작 때 전원 10000
- **도착 시간 = 남은 거리 ÷ 속도** → 가장 빨리 도착하는 유닛이 행동
  - 나머지 유닛은 그 시간 동안 (시간 × 자기 속도)만큼 앞으로 감
- 행동한 유닛은 남은 거리를 다시 10000으로 → 다시 달림
- 속도가 바뀌어도 남은 거리는 그대로, 도착 시간만 다시 계산
- **행동 당기기 30%** = 남은 거리에서 3000을 뺌 → 차례가 빨리 옴 (강탈 딜러가 새 버프를 얻을 때마다)
- 동시에 도착하면: 아군 → 직군(지원 → 공격 → 방어 → 회복) → 편성 순서
- 사이클(절대 턴): 지나간 시간을 누적해 첫 사이클 150, 이후 100마다 +1 → 별 미션·밸런스 기록용

**예시** (속도 100인 A, 속도 125인 B)

| 시점 | A 남은 거리 | B 남은 거리 | 누가 행동 |
|---|---|---|---|
| 시작 | 10000 (도착 100) | 10000 (도착 80) | B (80에 먼저 도착) |
| 80 지남 | 2000 (도착 20) | 10000으로 리셋 (도착 80) | A (20 뒤 도착) |
| 20 더 지남 | 10000으로 리셋 | 7500 (도착 60) | B |

- 속도가 1.25배인 B는 A보다 약 1.25배 자주 행동 → 속도 차이가 곧 행동 횟수 차이
- 화면 왼쪽 위 행동 순서 바가 이 계산으로 다음 8번의 순서를 미리 보여줌

**말할 내용 (30초)**
행동 순서는 "모두 같은 거리를 달리는 경주"라고 생각하시면 됩니다. 모두 10000을 달리고, 속도가 빠를수록 빨리 도착해서 먼저 행동합니다. 행동하면 다시 출발선으로 돌아갑니다. 그래서 속도가 1.25배면 행동도 약 1.25배 자주 하게 됩니다. 행동 당기기는 출발선을 앞당겨 주는 효과입니다.

## 3. AI와 일한 방식

**설계와 결정은 내가, 구현은 AI가**

| | 내용 |
|---|---|
| 기획서가 기준 | 규칙은 `GameDesign.md`에 먼저 정하고 AI는 그 문서를 따른다. 구현 중 바뀐 결정은 문서에 바로 반영 |
| 작업 규칙 문서 | `CLAUDE.md`에 주석 기준, 함수 분리, 검수 전 커밋 금지, Issue → PR 흐름을 적어 AI가 지키게 함 |
| 직접 검수 | 직접 플레이해 보고 OK한 것만 커밋. 문제가 보이면 고치게 하고 다시 확인 |

**말할 내용 (1분)**
제가 한 일은 "무엇을 만들지 정하고, AI가 그대로 만들었는지 확인하는 것"이었습니다. 게임 규칙은 기획서에 먼저 적고 AI가 그 문서를 기준으로 구현하게 했고, 작업 규칙 문서에 주석·함수 분리·커밋 시점까지 적어 매번 같은 방식으로 일하게 했습니다. 결과는 직접 플레이해 보고 괜찮을 때만 커밋했습니다.

> **캐릭터를 추가할 때 코드는 늘지 않게**
> 캐릭터는 코드가 아니라 데이터로 조립한다

**말할 내용 (15초)**
수집형 게임은 캐릭터가 계속 늘어납니다. 캐릭터마다 스킬 코드를 새로 짜면 코드도 버그도 같이 늘어납니다. 그래서 처음부터 "새 캐릭터를 만들 때 코드는 추가하지 않는다"를 목표로 잡았습니다.

## 5. 효과 블록 — 구조

**캐릭터 = 블록을 끼운 데이터**

```
CharacterData (SO 에셋 1개)
 ├─ 기본 정보, 스탯
 ├─ 1스 / 2스 / 3스  ─ 쿨타임, 대상 규칙, 효과 목록
 └─ 패시브 목록       ─ 발동 조건 + 효과 목록 + 횟수 제한
```

예: 강탈 딜러 3스 = 위에서부터 차례로 실행

1. 버프 수 비례 피해
2. 버프 전부 소모
3. 버프 강탈
4. 회복 (가한 피해의 50%)

- 스킬은 블록 종류를 몰라도 목록 순서대로 "실행"만 부른다
- 실행 방식은 블록마다 따로 구현 → **전략 패턴**
- 여러 캐릭터가 함께 쓰는 상태효과(화상·독·버프)만 별도 SO로 분리

**이렇게 하면 좋은 점**

| 좋은 점 | 설명 |
|---|---|
| 새 효과를 넣어도 기존 코드는 그대로 | 스킬 실행 코드는 "목록을 돌며 실행"만 하므로, 블록을 하나 추가해도 실행 코드·다른 블록·기존 캐릭터를 고치지 않음 |
| 한 번 만든 블록은 계속 재사용 | "피해", "상태효과 부여" 같은 블록은 대부분의 캐릭터가 함께 씀. 화상·독·버프도 같은 블록에 넣는 상태효과만 바꾸면 됨 |
| 순서로 결과를 조절 | 피해 → 격발이면 방금 붙은 화상까지 터지고, 피해 → 버프 소모면 버프가 피해에 반영된 뒤 지워짐. 코드가 아니라 목록 순서로 정함 |
| 문제가 생겨도 범위가 좁음 | 버그는 그 블록 하나에만 있으므로 고치는 곳도 한 곳. 고치면 그 블록을 쓰는 캐릭터 모두에 반영 |
| 수치 조정이 코드 밖에서 | 배율·턴 수·쿨타임은 Inspector 값이라 밸런스를 바꿀 때 코드를 다시 빌드하지 않음 |
| 설명도 자동 | 블록마다 "설명" 함수가 있어, 상세 창의 스킬 설명이 수치를 바꾸면 따라 바뀜 |

**말할 내용 (1분)**
캐릭터 하나는 데이터 에셋 하나입니다. 각 스킬은 "효과 블록 목록"을 가집니다. 강탈 딜러 3스는 블록 4개를 위에서부터 실행하는 것뿐입니다. 스킬 쪽 코드는 블록 종류를 몰라도 "실행"만 부르고, 실제 동작은 블록마다 따로 구현돼 있습니다. 새 효과가 필요하면 블록 하나만 추가하면 되고 기존 캐릭터는 건드리지 않습니다.

## 6. 효과 블록 — 조립 예시

**복잡한 스킬도 블록 조합으로**

| 스킬 | 블록 조합 |
|---|---|
| 하이퍼캐리 3스 (혼자 변신해 1 대 다) | 변신 + 아군 퇴장 + 경계: 고립 |
| 니콜 3스 | 상태효과 부여 (치명 확률·가속) + 다른 스킬 사용 (2스) |
| 격발 딜러 3스 | 피해 → 격발 |

- **순서가 결과를 바꾼다**: 피해를 먼저 넣고 격발하면, 그 피해로 방금 붙은 화상까지 함께 터진다

**말할 내용 (45초)**
하이퍼캐리 3스는 새 코드 없이 변신·아군 퇴장·경계 블록 3개를 조합했습니다. 니콜 3스는 "다른 스킬 사용" 블록 하나로 2스를 함께 씁니다. 블록은 순서대로 실행되기 때문에, 격발 딜러처럼 피해 다음에 격발을 두면 방금 붙은 화상까지 터집니다. 순서도 설계의 일부입니다.

## 7. 효과 블록 — Inspector 도구

**코드 없이 Inspector에서 조립**

[Inspector 스크린샷: 효과 블록 드롭다운]

- `[SerializeReference]`: 종류가 다른 블록을 한 리스트에 저장
- 직접 만든 드롭다운 에디터: 분류별 한국어 이름 + 마우스를 올리면 설명 툴팁
  - Unity 기본 Inspector에는 블록 종류를 골라 추가하는 UI가 없어서 만들었음
- 결과: 블록 27종으로 캐릭터 11명, 새 캐릭터는 에셋만 추가
- 지킨 규칙: 블록은 "네임스페이스 + 클래스 이름"으로 에셋에 저장되므로 폴더를 옮겨도 네임스페이스는 바꾸지 않는다 (바꾸면 조립해 둔 효과가 사라짐)

**말할 내용 (1분)**
조립은 Inspector에서 합니다. 종류가 다른 블록을 한 리스트에 담으려고 `SerializeReference`를 썼는데, Unity 기본 화면에는 블록을 고르는 UI가 없어서 분류별 한국어 드롭다운을 따로 만들었습니다. 그래서 기획자 입장에서도 코드를 몰라도 캐릭터를 만들 수 있습니다.

## 8. 핵심 ② 세이브 — 구조

**고정 데이터와 바뀌는 값을 나눈다**

| ScriptableObject (원본, 읽기 전용) | JSON 세이브 (바뀌는 값) |
|---|---|
| 캐릭터 스탯·스킬, 스테이지, 무기 종류 | 보유 캐릭터 ID·레벨·진급, 재화, 무기 개체, 가챠 카운터, 클리어 기록 |

- 세이브에는 **ID와 바뀌는 값만** 저장 → 불러올 때 ID로 SO를 찾아 연결
- SO는 전투 중에도 절대 수정하지 않음
- 파일 깨짐 방지: 임시 파일에 먼저 쓰고 다 쓰면 원본과 교체, 깨진 파일은 `.broken`으로 따로 보관
- 저장 시점: 가챠·레벨업·클리어 직후 바로 저장

**말할 내용 (45초)**
세이브는 원본 데이터와 바뀌는 값을 나눴습니다. 캐릭터 스탯 같은 원본은 SO에 두고, 세이브에는 ID와 레벨처럼 바뀌는 값만 저장합니다. 저장하다 꺼져도 파일이 깨지지 않게, 임시 파일에 먼저 쓴 뒤 교체합니다.

## 10. 핵심 ③ 가챠 판정 구조

**판정은 난수를 받아서, 결과는 뽑자마자 저장**

```
GachaService (모집 버튼)
  보석 확인 → 판정 → 지급·보석 차감·저장
      ↓ 난수를 넘겨줌 (System.Random)
GachaMachine (순수 C#)
  1회 판정만: 천장·소프트 천장·A 확정·반천 → 등급과 캐릭터·무기 결정
      ↓ 정해진 결과
GachaPresenter (연출)
  물레 → 한 장씩 공개 → 결과 목록. 보여주기만 함
```

- **난수를 밖에서 받는다**: 판정 코드는 난수를 직접 만들지 않고 받아서 씀
  - 실제 게임: 시드를 정하지 않은 난수 → 뽑을 때마다 결과가 다름
  - 검증: 시드를 고정한 난수를 넘기면 같은 결과를 다시 만들 수 있음 → 100만 회 시뮬레이션으로 확률 확인 (S 1.63%, 평균 61회)
  - 난수는 앱이 켜져 있는 동안 하나만 계속 씀: 매번 새로 만들면 짧은 시간 안에 같은 시드가 나와 결과가 겹칠 수 있어서
- **난수를 받는 방법**: `GachaMachine`을 만들 때 생성자 인자로 `System.Random`을 넘겨줌 (의존성 주입)
  ```csharp
  // GachaService: 앱이 켜져 있는 동안 쓰는 난수 하나. 시드를 정하지 않음
  private static readonly System.Random Random = new System.Random();

  // 뽑을 때 판정기에 그 난수를 넘겨줌
  var machine = new GachaMachine(Rules, Random, sCharacters, aCharacters, getWeapons);

  // 검증할 때는 시드를 정한 난수를 넘기면 매번 같은 결과
  var testMachine = new GachaMachine(rules, new System.Random(1234), ...);
  ```
  - 판정기는 그 난수의 `NextDouble()`(0~1 사이 수)로 등급 구간과 픽업 여부(반천)를 정하고, `Next(개수)`로 같은 등급 안에서 캐릭터·무기를 고름
  - 판정기가 난수를 직접 만들면 시드를 바꿀 방법이 없어 재현·검증이 안 됨 → 밖에서 받게 함
- **결과는 뽑은 직후 저장**: 연출을 시작하기 전에 카운터·캐릭터·보석을 저장

- **연출은 결과를 바꾸지 않음**: 5성인데 보라색까지만 빛나다 황금빛으로 바뀌는 "반전"도 결과가 정해진 뒤의 연출일 뿐
- 냥코 대전쟁과의 차이: 냥코는 시드를 저장해 두어 다음 결과가 미리 정해져 있음(예측 가능). 이 게임은 시드를 저장하지 않아 다음 결과를 알 수 없음

**말할 내용 (1분)**
가챠도 역할을 나눴습니다. 판정 코드는 난수를 직접 만들지 않고 밖에서 받습니다. 실제 게임에서는 매번 다른 난수를 넘기고, 검증할 때는 시드를 고정한 난수를 넘겨 100만 번 돌려 확률이 맞는지 확인했습니다. 그리고 결과는 연출 전에 바로 저장해서, 연출 도중에 게임을 꺼도 결과를 되돌릴 수 없게 했습니다. 연출은 정해진 결과를 보여주기만 하는데, 이건 다음 장의 전투 구조와 같은 원칙입니다.

## 예비 1. 가챠 확률 공시

**천장까지 넣은 실제 확률을 공시**

|---|---|---|

| 4성 무기 | 10% | 9.427% |

## 예비 2. 계산 방법 (마르코프 연쇄)

**카운터 상태의 흐름으로 계산**

```
0회 → 1회 → 2회 → … → 89회
 ↑___________________________|  S가 나오면 0회로
```

1. 가챠에는 카운터 상태가 있다: S 없이 몇 번 뽑았나, A 이상 없이 몇 번 뽑았나
2. 한 번 뽑을 때마다 다음 상태로 넘어가고, 다음 상태는 **지금 상태만 보고** 정해진다 → 마르코프 연쇄
3. 오래 돌리면 상태별로 머무는 비율이 일정해진다 (정상 분포)
4. 상태별 비율 × 그 상태의 S 확률을 모두 더하면 최종 확률

- 왜 계산으로 했나: 시뮬레이션은 돌릴 때마다 값이 조금씩 다르지만, 공시는 정확한 숫자가 필요해서
- 말하는 포인트: "AI가 제안한 방법이고, 공시가 정확해야 해서 택했고, 시뮬레이션으로 교차 검증했다"

그래도 장점이 있습니다. 캐릭터 스탯처럼 변하지 않는 원본은 SO에 두고, 세이브에는 ID와 바뀌는 값만 두었기 때문에, 원본 수치를 고쳐도 세이브를 다시 만들 필요가 없고 쉽게 깨지지 않습니다. 실제로 기능이 늘면서 세이브 구조가 7번 바뀌었는데, 버전 번호를 두고 예전 세이브를 새 구조로 바꿔 주게 해서 기존 세이브가 계속 이어졌습니다.

(클래스) 역할은 네 개로 나눴습니다. SaveData는 파일에 그대로 들어가는 내용이고, SaveStorage는 파일을 읽고 쓰기만 합니다. 쓸 때는 임시 파일에 먼저 쓰고 교체해서 중간에 꺼져도 안 깨지게 했습니다. PlayerProfile은 세이브를 불러오고 값을 바꾸면 바로 저장하는데, 화면은 세이브를 직접 만지지 않고 꼭 여기를 거칩니다. 마지막으로 GameDatabase가 세이브에 있는 ID로 원본 데이터를 찾아 연결합니다.

**[가챠]**
다음은 가챠 구조입니다.

가챠 연출은 여러 게임에서 레퍼런스를 가져왔는데, 물레를 돌리는 연출은 리버스: 1999라는 게임에서 가져왔습니다. 좀 비슷해 보일지 모르겠습니다.

가챠는 간단히 말하면 난수를 받아서 판정하고, 그걸로 결과를 정하는 방식입니다. 이때 판정 코드가 난수를 직접 만들지 않고, 밖에서 받아서 씁니다.
(클래스) 역할은 셋으로 나눴습니다. GachaService가 보석을 확인하고 뽑기를 진행해 결과를 바로 저장하고, GachaMachine은 천장과 확률 판정만, GachaPresenter는 정해진 결과를 물레 연출로 보여주기만 합니다.
방식은 이제 GachaMachine 이라는 갸챠를 관리하는 판정클래스를 만들 때 생성자 인자로 `System.Random`을 넘겨주고 그렇게 난수를 생성하게됩니다.
 확률을 검증할 때는 시드를 정한 난수를 넘겨서, 같은 결과를 몇 번이고 다시 만들어 보고 실제로 같은결과인가? 를 확인해볼수 있습니다.

냥코 대전쟁을 해 보신 분들은 아시겠지만, 그 게임은 시드를 저장해 두기 때문에 다음 결과를 미리 알 수 있고, 시드를 돌려서 원하는 걸 뽑는 일종의 편법이 있습니다. 이 게임은 실제 플레이에서는 시드를 정하지도, 저장하지도 않아서 다음 결과를 알 수 없습니다. 그리고 결과는 연출이 시작되기 전에 바로 저장되기 때문에, 연출 도중에 게임을 꺼도 결과를 되돌릴 수 없습니다.

**[로직과 연출]**
다음은 연출입니다.

전투 연출은 Claude의 도움을 받아 Unity 파티클과 빛 번짐 효과로 만들었는데요, 핵심은 이겁니다. "결과는 로직이 정하고, 화면은 재생만 한다."

메이플스토리를 해 보신 분들은 아시겠지만, 스킬을 누르면 모션이 다 나오기도 전에 몹은 이미 죽은 판정이 나고 경험치가 들어옵니다. 비슷한 개념이라고 보시면 됩니다. 이 게임도 행동 하나의 결과를 먼저 다 계산해 두고, 화면은 그 결과를 순서대로 보여주기만 합니다.

의도는 사실 모델링을 구하기 전이라 캡슐로 먼저 검증하고, 나중에 모델로 바꾸고 싶었던 거였습니다. 이렇게 나눠 둔 덕분에 나중에 보스를 골렘이나 드래곤 모델로 바꾸고 여러 번 수정할 때도, 전투 로직은 고치지 않고 이어갈 수 있었습니다.

(클래스) 코드로 보면, BattleManager가 전투 흐름을 진행하고 BattleUnit이 피해·사망·버프를 계산합니다. 계산하면서 "피해가 났다" 같은 사건을 BattleEvents로 알리기만 하고, BattleFxView가 그 사건을 받아 순서대로 재생합니다. 로직은 이미 끝났지만 HP바가 먼저 줄면 어색하니까, ShownHp가 화면의 HP를 붙잡아 두었다가 타격 순간에 맞춰 줄입니다.

**[마무리]**
정리하면, 캐릭터는 블록으로 조립하고, 세이브는 원본과 바뀌는 값을 나누고, 가챠와 전투 모두 결과를 정하는 부분과 보여주는 부분을 나눴습니다. [배운 점 한 줄] 남은 작업으로는 주요 캐릭터 모델링과 스테이지 밸런스가 있습니다.
